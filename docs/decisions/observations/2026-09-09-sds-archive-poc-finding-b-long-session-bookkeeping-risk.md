# A long governed-workflow session produced file-identity bookkeeping errors, all caught by pre-action re-verification before any incorrect action was taken

**Date:** 2026-09-09
**Context:** Cross-project evidence from the Portfolio repository's governed case-study workflow (Stretto Default Solutions / DMM Portal, Archive Phase 2) — an external project, not part of this repository — reviewed here for what it reveals about AIOM Core's approach to long-session execution risk and state verification. See the companion finding, [`2026-09-09-sds-archive-poc-finding-a-mechanical-resolution-and-owner-escalation.md`](./2026-09-09-sds-archive-poc-finding-a-mechanical-resolution-and-owner-escalation.md), for the same session's broader results.

## Finding

During the Archive Phase 2 session described in the companion finding, the executing session made three file-identity errors over the course of a long, high-volume reconciliation task (70 source files). In each case, the error was caught — not by any external check, but by the session re-verifying the specific source file immediately before acting on it — before any incorrect action reached the archive. The session itself reported that its own bookkeeping across the long session had become the weakest link in an otherwise successful phase.

## Why this matters for AIOM Core

AIOM Core already treats durable, repository-grounded state as more trustworthy than conversational continuity ("Durable state reduces dependence on conversational reconstruction," `seed/core.md`), and this repository closed a structurally identical problem for session *re-entry* under Initiative 13: nothing required a reasoning episode to revalidate `.aiom/` state before trusting it, and Initiative 9 Finding 8 established that a fresh session's *successful* reconstruction from durable state is not evidence that the reconstructed state was *valid* (see [`2026-08-28-i13-workflow-contract-owns-validation-invocation-cadence.md`](./2026-08-28-i13-workflow-contract-owns-validation-invocation-cadence.md) and [`2026-08-21-initiative-9-greenfield-poc-closure.md`](./2026-08-21-initiative-9-greenfield-poc-closure.md)).

This finding shows the same failure shape occurring *within* a single long session, not only across a session boundary: confident reasoning drifted from ground truth over the course of a long task, and the mitigation that worked was the same principle Initiative 13 already applies at re-entry — revalidate immediately before treating a specific piece of state as safe to act on — rather than any new deterministic machinery. No architecture in this repository currently generalizes that principle beyond session re-entry against the four durable `.aiom/` artifact types; it does not yet address in-session, per-action bookkeeping over external, non-`.aiom` artifacts of the kind this workflow was reconciling.

This is evidence directly relevant to treating increased workflow autonomy with caution: the one thing that caught all three errors here was a per-action verification discipline, not session-length management or an Owner checkpoint. Nothing in this repository currently defines a bounded-execution-unit or mid-session re-grounding requirement that would make that discipline something more than this session's own good practice — which is a real, not-yet-addressed gap directly relevant to any future exception-based autonomy that removes checkpoints without replacing them with something that preserves this kind of pre-action verification.

## Remaining limitation / falsification boundary

This is a single session's own account of its errors and corrections — there is no independent audit confirming exactly three errors occurred or that all were caught before an incorrect action; the corroborating evidence is the archive's clean 50-file, zero-mismatch checksum result at closure, not a separate review of the reconciliation work itself. It does not establish how this failure mode would behave at greater scale (Archive Phases 3–9, the Case Study Workflow, or a longer single session than this one), and it does not by itself indicate whether the correct response is a documentation/discipline change, a new checkpoint mechanism, or a bounded-execution-unit abstraction — that remains an open evolution-path question for Owner decision, not something this finding resolves on its own.
